# 与 Codex 版设计（agent-eta-codex-handoff）的对照

对照对象是 Codex 版设计交接包 `agent-eta-codex-handoff`（版本 0.1.0-design，未随仓库发布；其中的数学期望值已收录在 `plugins/agent-eta/tests/fixtures/codex-math-golden.json`）。它是一份交给 Codex 实现的 Go 版工程设计，包括设计文档、事件和状态契约、24 个回放场景、数学期望值；里面没有可运行的实现。
所以"效果是否类似"只能用两种方式检验：一是逐项比较两份设计，二是**把 Codex 包里可机读的测试材料拿来跑本插件**。两种都做了。

## 结论

1. **产品定义和核心算法几乎一样，而且是各自独立推出来的。**
   两边都拆成两个目标：本轮结束时间 T_c 和下一次需要人的时间 T_a；都明确不预测"代码是否被验收"。
   主算法都是"历史状态匹配 + 加权 Kaplan–Meier"：每个历史运行只取与当前状态最相似的一个快照，用 `n_eff=(Σw)²/Σw²` 衡量证据量，中断当删失样本处理，不调用模型，也不采信模型自报的进度。
2. **差异主要来自两个平台的接口能力不同，以及冷启动阶段怎么取舍。**
   Codex 的 hooks 给不出精确的授权等待时长，也没有状态栏，所以那份设计需要 daemon、notify 和进程包装器。Claude Code 有 `duration_ms`、async hook 和原生状态栏，这些都用不上。
3. **Codex 包里的测试材料在本插件里测出 7 个实际问题，另有 1 个是修复过程中顺带发现的，都已在 v0.2.0 修复。**
   7 个是：数值误差、重复计数、并行工具误解除权限等待、多请求并发、回测数据泄漏、离开窗口自动顺延、存储命令原文。
   顺带发现的 1 个是：`bash -c` 的内层命令可能泄漏进命令归类键。
   修复后全部数学期望值通过，移植过来的 16 个场景也全部通过。详见下文。

## 一致的部分

| 维度 | Codex 版 | 本插件（Claude Code） |
|---|---|---|
| 预测目标 | `T_c_turn`（本轮结束）、`T_a_signal`（关注信号）；不预测 `T_c_accepted` | T_c（完成）、T_a（需要你）；不预测验收 |
| 关注信号 | 权限请求、结构化输入、本轮返回、终态错误、宿主故障 | 权限请求、AskUserQuestion、ExitPlanMode、MCP elicitation、本轮结束、StopFailure |
| 主算法 | 历史状态匹配 + 加权 KM，每个 run 取一个快照，exp(−d) 权重 | 同左；另外加了自适应带宽和分层收缩（见差异第 8 条） |
| 删失 | 中断和失联标记为删失，不当成成功完成 | 同左（interrupted、session_end、abandoned 都算删失） |
| Stop 后继续 | Stop 只是"停止候选"，之后还有工具调用就恢复运行 | Stop 后如果出现同一个 prompt_id 的主线程工具事件，重新打开这一轮（Claude Code 自己的轮后辅助 agent 事件不算） |
| 终态后迟到的事件 | 不能重开 turn（INV-07） | 同左（有测试） |
| 子任务结束 | 不结束父任务（INV-03） | 同左 |
| 计划进度 | "3/5" 只作为弱信号，不当完成百分比 | 同左（`☰ 3/5` 只用作特征） |
| 解释 | 由特征变化生成，例如"计划新增 2 步" | 同左，例如"新增 2 次失败""计划扩张 5→7 步" |
| 存储 | 本地 SQLite，不上传遥测 | 同左 |

## 有意保留的差异

| # | 项 | Codex 版 | 本插件 | 理由 |
|---|---|---|---|---|
| 1 | 本轮完成的确认 | Stop 只是候选，由 `notify agent-turn-complete` 做权威确认 | Stop 就是终态；被 Stop hook 要求继续时按 prompt_id 重新打开 | Claude Code 没有单独的"本轮完成通知"。Stop 本身就是交还控制权的事件 |
| 2 | 人工等待时长 | hooks 模式下记为 unknown，这类运行不进入高质量样本 | 精确计算：批准时刻 = PostToolUse 时刻 − `duration_ms` | Claude Code 官方文档写明 `duration_ms` 不含授权等待；Codex hooks 没有这个保证 |
| 3 | 冷启动 | 无历史时显示"未知"，禁止使用硬编码先验 | 默认用先验，并在状态栏标出"先验"；满 5 次运行后先验按你的节奏校准，不再标"先验"；`cold_start: "unknown"` 可以切换成 Codex 的行为 | 数据少的时候先验反而最准（v0.2 在作者本机历史上：先验 113.4，学习版 133.4，B0 149.1）。v0.3 把先验校准到你的节奏后是 109.3 |
| 4 | 离开建议的门槛 | 要求 P(T_a ≤ h) ≤ 5%，并且有真实校准证书：每个窗口时长至少 100 次独立试验，Clopper–Pearson 上界 ≤5%；否则不显示 | 默认用经过小样本收缩的 P20 立刻显示；窗口账本满 100 个且上界 ≤20% 后标 ✓ | 单人使用可能要几个月才能拿到 Codex 那样的证书，期间完全没有建议。本插件给出"未验证"的建议，并如实记账，风险水平可以通过 `safe_quantile` 调 |
| 5 | 架构 | Go daemon、Unix socket、spool 队列、`agent-eta run -- codex` 包装器、单独开一个 watch 终端 | hook 直接写 SQLite；状态栏就在 Claude Code 里面 | Claude Code 原生支持 async hook（工具类事件不阻塞，约 45 ms）和状态栏，不需要常驻进程 |
| 6 | 后台子代理 | 父 turn 结束不等子任务 | 等后台子代理跑完再算结束 | 后台 agent 完成后，Claude Code 会用 `<task-notification>` 唤醒 Claude 继续工作，这段时间用户仍然不用管 |
| 7 | 仓库与路径 | 用 HMAC 处理 | 明文保存路径，但数据库文件是 0600、目录是 0700 | 在 watch 和报告里需要能分辨是哪个项目 |
| 8 | 相似度 | 固定权重 exp(−d)；样本不足时分层退回；首版不跨模型和权限模式借样本 | 自适应带宽的高斯核；三层收缩：本仓库相似运行 → 全部运行 → 校准先验；收缩强度 K0 用你自己历史的前瞻回放自动选 | 模拟数据上 pinball loss 比 B0 低 45%；小样本和真实历史上，自动选 K0 比固定值好 11–18% |
| 9 | 置信度 | 去掉总置信度，只展示样本量 | 保留"低/中/高"三档，同时显示 ESS | 三档有明确定义（ESS 加区间宽度），状态栏空间有限 |
| 10 | 数据保留期 | 事件 30 天，衍生数据 90 天 | 暂未实现 | 已列入路线图 |

## 两份设计各自更强的地方

**Codex 版更强：**

- 工程约束更严格：事件契约、传输层和业务层两级幂等、spool 队列、故障注入清单、TOML 最小修改、卸载冲突处理。
- 发布门槛有统计依据：pinball loss、Brier 分数、按 thread 切分数据、用冻结策略做影子试验、Clopper–Pearson 加 Bonferroni 校正。
- 隐私做得更彻底：路径和命令签名都用 HMAC，数据有保留期。

**本插件更强：**

- 已经能用，并且在真实的 Claude Code 2.1.278 上做过端到端测试。
- 能从已有 transcript 回填历史，第一天就有数据。
- 状态栏直接内嵌在 Claude Code 里，人工等待时长精确到秒。
- 正在运行的命令会用它自己的历史耗时来估计还要多久。
- 授权弹窗的风险单独建模，不混进任务本身的时长。
- 同时有模拟数据和真实数据的回测，并且和 B0、只用先验两个对照组比较过。

## 实测数字

回测时，每个预测点只使用当时已经结束的运行。

| 数据集 | 版本 | P50 命中率（理想 50%） | P80 覆盖率（理想 80%） | "可离开"违约率（理想 ≤20%） | 对比 B0（pinball loss） |
|---|---|---|---|---|---|
| 模拟数据（240 次运行，评估其中最后 80 次） | v0.2 / v0.3 | 50% | 85% | 7% | **低 45%**，满足 Codex 的发布门槛（≥10%） |
| 作者本机的真实历史（v0.2 时 24 次） | v0.2 | 72% | 89% | 27% | 低 19%，但只用先验的结果更好（71.7 vs 96.0） |
| 作者本机的真实历史（38 次） | v0.2 | 61% | 89% | 29% | 低 11%，仍不如内置先验（133.4 vs 113.4） |
| 作者本机的真实历史（38 次） | v0.3 | 59% | 90% | 11% | **低 27%**，并且好于内置先验（109.3 vs 113.4） |

真实历史目前样本太少，而且前后差别很大（早期多是运维长任务，后期多是短问答）。按 Codex 的标准来说，这仍属于 "experimental"，报告里会如实写出来。
v0.3 的改进来自两处：先验按你的节奏校准；收缩强度按你的历史自动选择（这 38 次上选出 K0=50，几乎完全依赖校准先验）。细节见 DESIGN.md 第 6、7 节。

## 如果要把两者合成一个产品

比较合适的边界是：

- **共用：** Codex 包里的规范化事件契约（`event.schema.json`）、状态契约，以及本插件的估计器。估计器是纯 Python，已经和 Codex 的数学期望值对齐。
- **按平台分别适配：** Claude Code 一侧用本插件的 hooks 和状态栏；Codex 一侧按那份设计，用 hooks、notify 和包装器。

这样同一套历史数据和同一个估计器可以同时服务两个 agent，这也是原始讨论最初的设想。
