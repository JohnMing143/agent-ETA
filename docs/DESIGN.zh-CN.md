# Agent ETA 设计文档

> 出发点是一段关于 "Agent ETA / Time to Attention" 的讨论记录（未随仓库发布）。这份文档说明它在 Claude Code 上怎么落地、哪些地方与原设想不同，以及已经验证到什么程度。

## 1. 产品定义（沿用讨论结论）

| 概念 | 定义 | 在界面上的呈现 |
|---|---|---|
| **T_c** 完成时间 | 距离 Claude 交还控制权的剩余时间（Stop hook） | `完成 ~4–9m`，即 P50 到 P80 的区间 |
| **T_a** 需要你的时间 | 距离下一次需要人的剩余时间：授权请求、AskUserQuestion、审批计划、MCP 输入，或者任务完成 | `可离开 ~3m → 14:52` |
| 置信度 | 由相似历史的有效样本量（ESS）和区间宽度决定 | `置信 低/中/高` |

几条设计原则：

- **给决策区间，不给假精确的时间点。** "可离开"取的是 T_a 的低分位（默认 P20），含义是"有 80% 的把握在这之前不会需要你"。
- **看行为，不听它自报。** 呼应讨论里引用的 *The Unreliable Progress Bar*：模型从不参与估计，插件只观察 hooks 事件。
- **第一版不用机器学习框架。** 只用可测试的非参数统计，纯 Python 标准库实现。每一次运行都会自动变成一条带标签的训练数据。

## 2. 从 Codex 到 Claude Code 的映射

| 讨论里基于 Codex 的设想 | Claude Code 里的对应 | 说明 |
|---|---|---|
| `UserPromptSubmit` 开始计时 | `UserPromptSubmit`（同步 hook） | 同名 |
| `PreToolUse`/`PostToolUse` 轨迹 | 同名（async hook，不阻塞 Claude） | `PostToolUse.duration_ms` 就是 Codex 的 command `durationMs` |
| `PermissionRequest` = 需要人 | `PermissionRequest`，加上 `Notification(permission_prompt)` 作为兜底 | 另外把 `AskUserQuestion`、`ExitPlanMode`、`Elicitation` 也记为需要人 |
| `SubagentStart/Stop` | 同名 | 另外还有 `Stop.background_tasks`，见第 3 节 |
| `Stop` = ground truth | `Stop`，异常结束时是 `StopFailure` | 用户按 Esc 中断时**不会**触发 Stop，见第 3 节 |
| `Interrupt` | 没有对应事件 | 在下一次 `UserPromptSubmit` 时推断，并记为删失样本 |
| App Server `turn/plan/updated` | `TaskCreated`/`TaskCompleted` hook，以及 `TodoWrite` 的工具输入 | Claude 5 系列模型默认不开启，所以只作为可选信号 |
| App Server `tokenUsage` | statusLine 输入里的 `context_window` | 目前没用上，列入路线图 |
| "本地 companion process" | statusLine 命令本身（`refreshInterval: 5`） | 不需要常驻进程 |
| 插件分发 | Claude Code plugin 加本地 marketplace | `hooks/hooks.json` 配合 `${CLAUDE_PLUGIN_ROOT}` |

## 3. 在 Claude Code 上实现时的关键发现

这些都是在 Claude Code 2.1.278 上逐条核对官方文档、再用真实会话做端到端测试后确认的：

1. **Claude 5 系列模型默认没有任务清单工具。** 按官方文档，TaskCreate 和 TodoWrite 默认只在 Opus 4–4.7、Sonnet 4–4.6、Haiku 4.5 等模型上可用。所以社区现有的 `task-progress-bar` 那种"数 todo"的 ETA，在 Opus 5 上基本拿不到数据。这反过来印证了"看行为"这条路线。
2. **按 Esc 中断时 Stop 不触发。** 插件在下一次提交 prompt 时关闭这一轮，并标记为 `interrupted`。这样的样本进入 Kaplan–Meier 时按**删失**处理（我们知道它"至少跑了这么久"），不会被丢掉，也不会被当成正常完成。
3. **`duration_ms` 不包含授权等待。** 因此"用户批准的时刻 = PostToolUse 的时刻 − duration_ms"可以精确算出。人的等待时间会从 agent 的有效工作时间里扣掉，避免"你去倒了杯水"这种情况污染训练数据。
4. **后台子代理会把一轮拆成两段。** 流程是：`Stop` 时 `background_tasks` 不为空，Claude 先停下来；子代理完成后，Claude Code 以 `<task-notification>` 作为 prompt 再次触发 `UserPromptSubmit`。插件把这两段识别为同一轮工作（端到端测试里实际遇到过这种拆分，已经修复）。
5. **插件不能自己设置 statusLine。** 插件的 settings.json 只支持 `agent` 和 `subagentStatusLine`。所以需要 `/agent-eta:setup` 往用户的 settings 里写一个启动脚本，脚本再通过 `plugin_root` 指针找到当前版本的插件，插件升级后也不用重新设置。
6. **transcript 里有 `turn_duration` 记录。** 所以可以把 `~/.claude/projects/*.jsonl` 重放进同一套 hook 处理逻辑，第一天就有个性化的历史数据。
7. **SessionStart 不一定带 model 字段**（在 `-p` 模式下实测为空）。退路是在 Stop 时读 transcript 末尾的 assistant 记录，或者从 statusLine 的输入里补上。
8. **`UserPromptSubmit`/`SessionStart` 的 stdout 会被注入到 Claude 的上下文里。** 所以所有 hook 都一律不输出任何内容。插件对上下文的开销只有两个 skill 的描述，约 216 token。

## 4. 架构

```
Claude Code ──hooks(18 个事件)──► eta.py hook ──► ingest.py ──► SQLite (~/.claude/agent-eta/eta.db)
   │                                                               ▲        │
   │  statusLine(每 5s + 事件驱动)                                  │        │ 每轮结束时写入标签
   └────────────► statusline.sh ─► eta.py statusline ─► estimator.py┘        ▼
                                          │                    snapshots(轨迹状态 → 剩余时间)
                                          └─► render.py ─► "⏱ 3:12 │ 完成 ~4–9m │ 可离开 ~3m"

~/.claude/projects/*.jsonl ──► backfill.py ──(重放为同样的 hook 事件)──► ingest.py
/agent-eta:eta ──(! 动态注入)──► eta.py status / report ──► Claude 总结给你
```

| 文件 | 职责 |
|---|---|
| `scripts/eta.py` | 入口。第一行就记录事件时间戳，避免 async hook 的启动延迟造成偏差 |
| `agent_eta/ingest.py` | 维护一轮运行的生命周期：中断、晚到的 async 事件、Stop-hook 续跑、后台唤醒、`!` 命令之后的回应（单独一轮，从命令结束开始计时）、授权等待的计算 |
| `agent_eta/features.py` | 纯函数：命令归类（`npm test`、`pytest`……）、prompt 分类（中英文）、阶段判定 |
| `agent_eta/estimator.py` | 估计器（第 6 节） |
| `agent_eta/tuning.py` | 按你自己的历史回放，自动选择收缩强度 K0（第 6 节第 3 条）；后台重选 |
| `agent_eta/report.py` | 历史统计、实时预测的准确度、回测 |
| `agent_eta/backfill.py` | transcript 导入 |
| `agent_eta/setup.py` | 安装和卸载状态栏（保留原有状态栏），以及 doctor 自检 |

## 5. 数据模型

- `runs`：一行对应一轮（一个 prompt 到交还控制权）。包括静态特征（仓库、模型、effort、权限模式、prompt 类别和长度）、实时计数、等待人的累计时间，以及标签 `active_s`。
- `snapshots`：每完成一步记录一次轨迹状态（已用时间、工具数、阶段、失败次数、计划进度、子代理数）。一轮结束时回填两个标签：`rem_done_s`（剩余完成时间）和 `rem_attn_s`（剩余需要人的时间），外加删失标记。**这就是讨论里说的 `trajectory_t → remaining time` 监督数据。**
- `tool_calls`：每次工具调用的耗时，用来预测正在运行的命令还要多久。
- `attention`：每次需要人的事件（类型、时刻、等了多久）。
- `attention` 里每条请求都绑定到对应工具调用的 `tool_use_id`，逐个关闭；等待时长取所有请求的并集。
- `predictions`：状态栏当时显示过的预测，事后用来和真实结果对账。
- `windows`（v0.2 新增）：状态栏真正给出过的每一个"可离开"窗口，记录发出时间、时长和固定的到期时间。撤销也只做标记，不删除。每个窗口事后都会判定为守住、违约或结果未知。
- `tuning`（v0.3 新增）：自动选出的 K0、选择时用了多少运行和预测点、每个候选的得分，以及后台重选的占位标记（防止多个 hook 同时启动重选）。

## 6. 估计器

所有组成部分都表示为**生存曲线** S(t) = P(剩余时间 > t)。这样各部分可以按概率规则组合，而不是把几个点估计取平均。
从 v0.2 起，曲线可以在任意 t 精确求值，不再做网格插值。Kaplan–Meier 是精确的阶梯函数；求分位数时，每个跳变点都是精确的取值点，连续部分用二分法求解。纯数学层（`KaplanMeier` 类）与 Codex 包的 `math-golden.json` 逐项一致，超出观测范围时返回 null。

1. **先验。** 用 LogNormal 分布，中位数由任务类别 × effort × prompt 长度决定。计算时先以已用时间 e 为条件，即 P(T−e>t | T>e)，因为分布是重尾的，已经跑得越久，剩下的往往也越久；再按阶段缩放（例如测试通过后乘以 0.35）。
   **v0.3 起先验会按你的节奏校准**：在对数时间上，用已正常结束的运行估计三样东西——整体快慢、每类任务的快慢、离散程度（σ）。每一样都用 5 个伪样本向内置值收缩，每类任务再向整体收缩。只有这几个参数，方差远小于近邻曲线，所以从 5 次运行起就有用。和近邻一样只用"当时已经结束"的运行，回测里没有未来信息。
2. **学习。** 从每个历史运行里取出**与当前状态最相似的那一个快照**，然后对这些快照的剩余时间做加权 Kaplan–Meier。
   - 全局层：只按"当前阶段"匹配，即已用时间、工具数、阶段、失败次数、计划进度和子代理。
   - 局部层：在全局层的基础上，再按仓库、模型、effort、任务类别和 prompt 长度匹配。
   - 核函数是高斯核，带宽自适应：取第 k 近邻的距离作为带宽，k≈√N。数据少时自动放宽，从所有历史里借信息；数据多时只看真正相近的运行。
3. **分层收缩。** 先算 S_global = mix(KM_global, 校准先验)，再算 S = mix(KM_local, S_global)，每一层的权重都是 ESS/(ESS+K0)。证据不足时，自动退回到更宽的那一层。
   **K0 按用户自动选择**（v0.2 固定为 3）。同一个 K0 在不同的历史上表现相反：几十次杂乱的运行，K0=∞（只用校准先验）最好；几百次相似的运行，K0=3 最好；使用习惯在漂移时也是小 K0 好。
   所以 `tuning.py` 在候选 3 / 8 / 20 / 50 / ∞ 中，用你自己历史的前瞻回放打分：每个预测点只用当时已结束的运行，损失是状态栏显示的三个分位数（完成 P50、P80，需要你 P20）的对数 pinball loss 取平均。用对数是为了不让几次超长运行主导结果。少于 20 个可评分点时用默认值 8。
   历史满 10 次时第一次选；之后已结束运行每增长 10%（至少 5 次），Stop hook 在后台起一个独立进程重选（stdin/stdout/stderr 都接 /dev/null，并且脱离会话，不会拖住 Claude Code）。
4. **正在运行的工具。** 例如一条 `npm test` 已经跑了 40 秒，就用同一个仓库里这条命令的历史耗时，在"已经跑了 40 秒"的条件下算出剩余分布，作为 T_c 和 T_a 的下界（S = max(S, S_tool)）。
5. **授权风险。** T_a 额外乘以 exp(−λ·p·t)。其中 λ 是这一轮的工具调用速率，p 是当前权限模式下每次调用触发授权的概率（从实时数据学习，以先验作为伪计数）。
6. **任务清单**（如果有）。用步骤完成间隔的 EMA（α=0.3，即 Codex 设计中的 B1 基线，也是 task-progress-bar 的做法）外推剩余步数，与学习结果混合，权重上限 0.5。一次勾掉多步的批量更新不参与 EMA。
7. **"可离开"的小样本保守修正。** 取分位 q_eff = 0.2·(ESS+1)/(ESS+1+SAFE_K)。承诺过长的代价（你走了，Claude 在等你）比承诺过短高，而在小样本或分布漂移时，低分位会被高估。
   v0.4 起 SAFE_K 也按用户选（默认 6，候选 0 / 2 / 6 / 15 / 40）：在 K0 的同一次回放里，优先取回测违约率 75% 置信上界 ≤ `safe_quantile` 的最宽松候选；没有的话取承诺次数 ≥20、实测违约率最低且不超标的候选；再没有就用默认值，默认值本身超标时收紧一档（小样本下违约率不一定随保守度单调下降，所以不直接跳到最保守）。回放里的"需要你"不含授权弹窗（导入的历史里没有），所以最近 30 天真实窗口的账本是最后一道检查：违约率上界超过目标时，每次重选都比上次再保守一档。
   窗口一旦发出，到期时间就固定下来，不随刷新顺延。出现需要你的事件，或者新估计已经撑不到原到期时间的一半时，窗口会被撤销。所有窗口都进入账本，累计满 100 个、且不利结果（违约加未知）的单侧 95% Clopper–Pearson 上界 ≤ `safe_quantile` 之后才标 ✓。
8. **解释。** 每次估计都附带一组依据，例如"参考 12 次相似历史""按你 38 次历史校准：这类任务约为默认估计的 ×1.8""正在运行 npm test，已 40s，历史中位 1m""验证失败 2 次"。和上一次预测相比如果明显变长，状态栏会显示 ↑，并在依据里给出原因（例如新增了失败）。

**性能（v0.3）。** 状态栏每次刷新都要重建近邻池并求分位数，v0.3 做了三处与结果无关的优化，回放输出与 v0.2 逐位一致：
所有曲线都单调不增，所以求分位数时在跳变点上二分查找，不再逐点求值；近邻池只取需要的列、用元组行，快照特征按需计算；
每个历史运行的"最相似快照"按已用时间排序后从当前时刻向两边搜索，一旦"已用时间"这一项本身就超过当前最优距离就停止（它是整个距离的下界，所以结果仍是精确最近邻）。
另外 hook 和状态栏不再导入 argparse、statistics、traceback、subprocess，正则在第一次用到时才编译；原有状态栏命令改为和我们的计算并行执行。

## 7. 验证

**单元测试共 62 个**，在 Python 3.8 和 3.13 上都跑过（Docker 官方镜像）。

- 覆盖的场景包括：生命周期、授权等待的扣除、中断删失、晚到的 async 事件、Stop-hook 续跑、Claude Code 轮后辅助 agent 不会重开已结束的一轮、后台唤醒、`!` 命令的回应单独成轮（实时和导入）、transcript 导入、setup 保留并恢复原有状态栏、拒绝覆盖无法解析的 settings.json。
- 有一个基于模拟数据的**校准检验**，断言 P50/P80 的命中率落在合理范围内，并且学习版的误差不高于只用先验。
- v0.2 新增了三组测试：
  - **Codex 数学期望值**：KM、条件分位数、EMA、ESS、Clopper–Pearson，全部值通过，容差 1e-9。
  - **16 个 Codex 场景不变量**：移植成 Claude Code 事件。
  - **隐私**：把带 token 的命令跑一遍，然后在数据库文件里搜索那个 token。
- 还有窗口账本的测试：到期时间固定，撤销后仍然计分。
- v0.3 新增：先验校准能学到你的节奏且不看未来；自动调参选出得分最低的候选并持久化；只有历史增长够多才触发重选；heredoc 正文、`grep pytest` 这类参数不会被当成命令；被拒绝的命令不会一直显示为"运行中"。

**模拟基准。** 用 `tests/sim.py` 生成 240 次运行，其中埋了真实存在的结构：任务类型决定工作量；web 仓库的测试要跑 90 秒，api 仓库只要 25 秒；测试失败会触发修复循环。回测时，每个预测点只能使用当时已经结束的运行：

| | P50 命中率（理想 50%） | P80 覆盖率（理想 80%） | "可离开"违约率（理想 ≤20%） | 典型误差 |
|---|---|---|---|---|
| 学习 | **50%** | **85%** | **7%**（304 次 ≥1 分钟的承诺） | ×1.3 |
| 仅先验 | 63% | 98% | –（给不出承诺） | ×1.4 |

以上是 v0.2 的数字，v0.3 在这组数据上不变（自动选出 K0=3，pinball 26.3）：评估最近 80 次运行，曲线全部精确求值。和 Codex 设计的 B0 基线相比，学习版的平均 pinball loss（P50 和 P80 取平均）是 26.2，B0 是 47.7，**低 45%**，满足 Codex 设定的发布门槛（至少低 10%）。

**小样本与漂移（v0.3 新增的对照）。** 同样的回测，换成更接近"刚安装"的数据：

| 数据 | v0.2 | v0.3 | 内置先验 | B0 | v0.3 选出的 K0 |
|---|---|---|---|---|---|
| 模拟 240 次 | 26.2 | 26.3 | 46.5 | 47.7 | 3 |
| 模拟 40 次（3 个种子） | 35.2 / 38.2 / 40.7 | **30.5 / 28.7 / 32.0** | 45.6 / 44.4 / 44.1 | 51–55 | ∞ |
| 漂移（前 60 次慢测试，后 60 次换仓库） | 46.3 | 46.4 | 55.5 | 91.7 | 3 |
| 作者本机真实历史 38 次 | 133.4 | **109.3** | 113.4 | 149.1 | 50 |

表中是平均 pinball loss（完成 P50 和 P80），越低越好。v0.3 的 K0 是在同一段历史上选的，有轻微的"样本内"乐观。为此另外做了严格的前瞻检验：每个预测点只用在它之前就已结束的运行来选 K0。在 6 组数据里，有 5 组和事后最优的固定 K0 只差 0–2%，漂移那组差 9%（但仍比固定 K0=∞ 好 23%）；在小样本和真实数据上比 v0.2 的固定 K0=3 好 11–18%。

后半段是差距最大的地方。验证阶段学习版的误差是 ×1.3–1.4，先验是 ×4–7；修复循环中学习版是 ×1.3–1.5，先验是 ×1.9–4.8。换句话说，"测试已经过了，马上就好"这类规律确实是从数据里学出来的。

**作者本机真实历史**（v0.3 时从 transcript 导入 38 次运行；v0.2 时是 24 次）。

- v0.2：纯学习版的 pinball loss 反而比内置先验差（这 38 次上是 133.4 对 113.4），"可离开"违约率 29%。
- v0.3：自动选出 K0=50，几乎完全依赖校准先验。pinball loss 109.3，低于内置先验，比 B0（149.1）低 27%；"可离开"违约率 11%（18 次承诺）；P80 覆盖率 90%。
- 仍然偏粗：P50 的典型误差 ×2.3（内置先验 ×2.1）。

### 7.x 学习到底有没有用（v0.5，2026-09-25，作者本机 65–67 次真实运行）

指标和调参一样：完成 P50/P80、需要你 P20 的对数 pinball loss；每个点只用当时已结束的运行；95% 区间来自按运行分组的 bootstrap（同一次运行里的点不独立）。

| 实验 | 结果 |
|---|---|
| 按时间回放，v0.4.2 的估计器 vs 内置先验（完全不学习） | +1.2%，区间 [−6.3%, +8.4%]，**证明不了** |
| 固定考题（最近 20 次），给 0 → 46 次更早的历史 | 越多越差：−9.6% [−22.6%, +2.5%]，P50 命中 69% → 77%——**漂移**：最近的任务比早期短 |
| 可交换学习曲线（轮流当考题） | K0=50 从 20 次到 65 次持平；重度依赖近邻的 K0=8 从 30 次到 65 次显著变好（+3.7% [+1.0%, +6.5%]），但仍不如先验 |
| 残差离散 | 按类别校准后 sigma≈1.27：只凭开局信息，50% 区间就有 ×2.3 宽，典型误差 ×2.2 已贴着这个底 |
| 分位数重校准（按时间前瞻学习） | P50 命中 62% → 52%，P80 覆盖 92% → 83%；损失改善约 3%（区间含 0） |
| 近期权重半衰期 60 → 0.5 天 | 最近 20 次 +2.9% → +6.9%（K0=50）/ +9.6%（K0=20），单调变好；区间下界略低于 0 |

据此 v0.5 把半衰期和重校准交给自动调参。在同一份历史上重新评估（`eta.py eval`）：整体 +7.4% [−0.3%, +13.7%]，最近三分之一 +14.0% [+3.4%, +22.0%]（显著），P50 命中 54%、P80 覆盖 84%、典型误差 ×2.43 → ×2.12；学习曲线上更早历史的边际收益 +1.0% [−2.4%, +4.3%]。

结论：对这类高度随机的任务，**个人化的长期记忆几乎不带来可测的提升**；可测的提升来自最近的上下文（同一天、同一会话）和对系统性偏差的重校准。注意半衰期是 4 个候选里在同一份数据上挑的，数字略偏乐观；重校准和 eval 本身是严格前瞻的。

### 7.y 跨用户验证与"可离开"的可靠性（v0.5.1，2026-09-25）

数据：作者本人 68 次运行，加上公开数据集 trace-commons/agent-traces（原始 Claude Code 会话 JSONL，CC-BY-4.0，捐赠者同意）里的 28 个会话，按项目路径分成 5 位贡献者（267 / 34 / 15 / 11 / 10 次运行），用插件自己的 backfill 导入到隔离目录。每位贡献者当作一个独立用户，各自调参。复现脚本：`agent-eta-research/cross_user.sh`（不在插件里）。另一份公开数据 semianalysisai/cc-traces 只有请求级计时，没有工具和"需要你"的事件，无法可靠切分轮次，未使用。

**学习效果（`eta.py eval`）**：267 次那位（单轮中位 52 秒）+27.7% [+19.2%, +35.6%]，几乎全部来自节奏校准（只校准 +28.3%）；自动调参给他选了 K0=8、半衰期 60 天、重校准开——和作者（半衰期 0.5 天）完全不同。其余几位 −3% 到 +1%，区间都含 0，内置先验本来就贴合。校准后残差 σ：作者 1.27，公开数据合计 1.43。

**"可离开"：先试的 ACI（自适应共形推断）没有采用。** 教科书式 ACI 保证的是"逐点"误差：每个时刻的 20% 分位窗口被突破的比例收敛到 20%。但大部分时刻的窗口不足 1 分钟、根本不显示，显示出来的长窗口恰恰是模型最没把握的地方：267 次那位逐点误差 20%，显示的承诺违约 34–51%。只用显示出的承诺更新（以及按结果揭晓时的水平反推）的变体，在作者身上后半段违约 26–28%，承诺分钟反而比现有的 SAFE_K 少；零历史的先验加 ACI 也做不到"第一天就守住 20%"。批量的选择性风险控制（按 Clopper-Pearson 上界逐档检验）在这些样本量下几乎不给承诺。

**按时间完整回放上线过程**（每到本该重新调参的时刻，截取那一刻之前的数据库跑 `tuning.tune`；模拟中给出的承诺写进窗口账本，后续调参能看到）：

## 8. 与讨论设想的差异和取舍

- **用 kNN 快照加 Kaplan–Meier，而不是先做 `Σ E(T_i | step type)`。** 在 Claude 5 模型上通常没有显式的计划步骤，而轨迹快照在任何模型上都能拿到。这种做法与讨论里"survival model / quantile regression"的升级方向一致，只是换成了非参数版本：不需要训练过程，数据越多越准，而且删失样本能被正确使用。
- **授权风险单独建模。** 授权请求是否出现，取决于你的 allow 规则，而不是任务本身。所以它不混进任务的学习标签，而是作为一个随权限模式变化、可以在线更新的风险率，乘到 T_a 上。
- **状态栏不需要常驻进程。** 用 `refreshInterval` 每 5 秒重新计算一次；代价是状态栏刷新时多约 0.06 秒的 CPU。
- **先验不写死，也不全交给近邻。** 先用几个参数把先验校准到你的节奏（低方差），再让回放决定近邻能压过它多少（K0）。这比固定一个收缩强度更稳：同一个值在"少而杂"和"多而像"的历史上表现正好相反。

## 9. 路线图

1. **通知。** 在"需要你"那一刻推送到手机（ntfy、Bark 等），与"可离开到 14:52"配成一对。
2. **Codex 适配器。** 按 Codex 交接包的事件契约（`event.schema.json`）把 Codex 的 hooks 和 notify 映射到同一套 ingest，这样一个估计器可以同时服务两个 agent（讨论里的原始目标）。对照见 [CODEX_COMPARISON.md](CODEX_COMPARISON.md)。
3. **数据保留期**（参照 Codex 设计：事件 30 天，衍生数据 90 天），以及路径 HMAC 的可选模式。
4. **更多特征。** token 速率（statusLine 的 `context_window`）、diff 大小、prompt 的语义嵌入（仍然在本地计算）。
5. **数据量大了之后（例如超过 500 次运行），换成分位数回归或生存森林，与现在的 kNN-KM 做 A/B 回测，按回测结果决定是否切换。**
6. **跨机器同步历史**（可选），以及 IDE 里的进度显示。
