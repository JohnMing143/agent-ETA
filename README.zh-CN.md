# agent-ETA —— 编程 agent 能告诉你“现在可以走开多久”吗？

我们做了一个 Claude Code 插件，想在**你把任务交给 agent 的那一刻**回答两个问题：
*这件事要多久*，以及*在它需要你之前，你可以放心离开多久*。
然后我们尽可能严格地检验了它：用作者自己的历史，也用别人公开分享的 Claude Code 会话数据（不同的人、不同的模型，约 2,000 轮，11 份历史）。

**一句话结论：** 诚实的时长估计可以做，但只能是粗略的（任务开始时误差中位 ×2.3–2.6）。*又可靠又有用*的“可离开时间”做不到，原因是结构性的：跑过第一分钟之后，编程 agent 交还控制权的概率几乎恒定在**每分钟 12–19%**，不管它已经干了多久。没有额外信息的话，80% 能守住的窗口在任何时刻都只有 1–2 分钟。我们试过的大多数突破办法都没有成功——这份文档把试了什么、测到了什么、下一步会怎么试都记录下来。

插件本身仍然可用、可以安装（见 [docs/plugin.zh-CN.md](docs/plugin.zh-CN.md)）；这份 README 讲的是我们学到的东西。

## 1. 做了什么

一个纯被动的 Claude Code 插件（hooks + 状态栏，只用 Python 标准库，不调用模型，不往 agent 的上下文里注入任何东西）。每一轮都变成一个带标签的样本：每一步工具调用时的轨迹、还剩多久、什么时候需要你（完成、提问、要授权）。状态栏类似：

```
⏱ 0:05 │ 完成 ~2–8m │ 可离开 ~1m → 14:32 │ 置信 中
```

估计器由几部分组成：按任务类型（提问 / 修复 / 功能……，由关键词、prompt 长度、effort 决定）的内置先验，校准到**你自己的节奏**；你过去**相似时刻**的 Kaplan–Meier 曲线（静态特征 + 轨迹：工具数、失败、阶段、计划进度），和先验按学到的收缩强度混合；授权弹窗和正在执行的已知慢命令的风险；以及“可离开”窗口——注意力时间的一个低分位，带固定到期时间记进**账本**，事后逐个核对，承诺永远要和真实发生的事情对账。

所有参数都按每个人自己的历史回放来调（见第 3 节）。设计细节见 [docs/DESIGN.zh-CN.md](docs/DESIGN.zh-CN.md)。

## 3. 怎么评估

这个问题里很容易骗到自己，所以下面每个数字都遵守这些规则：

- **按时间前瞻**：每个预测只用它之前已经结束的运行，重校准和调参也一样，谁都不能看见未来。
- **把整个线上系统按时间重演一遍**：“可离开”的可靠性是这样测的——假装插件从第一天就装着：每到本该重新调参的时刻（满 10 次运行，之后每增长 10%），截取那一刻之前的数据库跑调参，用这组参数直到下一次调参；给出的每个承诺都写进账本，让反馈回路像真实使用时一样起作用。
- **只算用户看得到的**：一个承诺只有在会被显示时才算（≥1 分钟，按显示的档位向下取整）。“逐时刻”的覆盖率可以很完美，而显示出来的承诺却错得离谱（见第 5 节 ACI）。
- **不确定性用按运行分组的 bootstrap**：同一轮里的点不独立；只有 95% 区间不含 0 才算“已证实”。
- **损失**：所显示分位数（完成 P50、P80，需要你 P20）的对数 pinball loss。

插件自带 `eta.py eval`，任何人都可以在自己的历史上核对这些说法。

## 4. 发现

### 4.1 任务开始时，时长就是一个 ×2.5 的猜测——对谁都一样

按任务类型校准每个人的节奏之后，一轮时长（对数）剩下的离散 σ≈1.27（作者）到 1.43（公开数据合计）：50% 区间约 ×2.3 宽。开局时能用的信息我们都试了：

| 任务开始时的信息 | 误差中位 | 和实际（对数）的相关 |
|---|---|---|
| prompt 长度 + 关键词类别 + 你的节奏（插件） | ×2.60 | 0.1–0.4 |
| + 你过去最相似的 prompt（字符 n-gram TF-IDF，本地） | ×2.51 | – |
| 等 15 / 30 / 60 秒看 agent 最初的动作 | ×2.4–2.7 | – |
| 让大模型（Claude Haiku）读任务和上一轮回复，再按你校准 | ×2.46–2.59 | 0.3–0.5 |
| 插件 + 大模型融合 | **×2.29** | – |
| agent 自己列出的计划（TaskCreate / TodoWrite），如果列了 | 一位用户 ×1.62（21 个任务），另一位更差 | 0.77 / 0.18 |

光看需求文字，信息量不够：“修一下这个 bug”可能一分钟，也可能半小时，取决于 agent 读代码后发现了什么。唯一明显突破的，是 agent 看过代码之后自己列出的计划——而我们数据里的大多数 agent 几乎从不列计划。

### 4.2 agent 交还控制权的速率几乎恒定

在 8 份历史的 918 个任务上，“下一分钟内需要你”（完成、提问或要授权）的概率：

| 已进行 | 仍在跑的任务 | 下一分钟需要你 | 据此 80% 能守住的窗口 |
|---|---|---|---|
| 0 分钟 | 100% | 39% | 0.4 分钟 |
| 1 分钟 | 61% | 19% | 1.0 分钟 |
| 2 分钟 | 49% | 18% | 1.1 分钟 |
| 3 分钟 | 40% | 13% | 1.6 分钟 |
| 5 分钟 | 30% | 14% | 1.5 分钟 |
| 8 分钟 | 19% | 12% | 1.8 分钟 |
| 12 分钟 | 12% | 11% | 1.9 分钟 |

第一分钟过后，这个风险几乎不下降：一个任务已经跑了多久，几乎不能告诉你它还要多久。这是交互式编程 agent 的性质——它几乎在任何一步之后都可能觉得“做完了”——而不是估计器的问题。第 5 节的一切都由此而来：没有针对具体任务的信息，80% 的承诺就只有 1–2 分钟，换什么方法都一样。“先等 90 秒，还在跑就可以离开 W 分钟”这种两段式安排，W 也只有 1–1.5 分钟，原因相同。

放宽把握也没多大用（合计，回放）：

| 把握 | 给出承诺的时刻 | 平均承诺 | 违约 |
|---|---|---|---|
| 90% | 3% | 1.2 分钟 | 21% |
| 80% | 17% | 1.3 分钟 | 21% |
| 70% | 38% | 1.4 分钟 | 27% |
| 60% | 58% | 1.7 分钟 | 35% |
| 50% | 70% | 2.3 分钟 | 46% |

### 4.3 “可离开”的可靠性因人而异

把最终设计在全部 11 份历史上按时间重演：**显示出的 400 个承诺违约 24.5%（95% 上界 28.3%）**，高于 20% 的目标；承诺不少于 20 次的历史之间，从 8% 到 45% 不等。几乎所有违约都是 agent 在一轮刚开始时给出“1 分钟”承诺后**提前干完了**。一轮的时长是双峰的（几十秒的快问快答 vs 几分钟的工作），快问快答多的人，短承诺最容易被打破。

作者的真实使用（不是回放）：281 分钟的 agent 工作里，219 分钟（78%）落在“至少 3 分钟不需要你”的空当里。插件守住的窗口加起来 138 分钟——但那是**121 个 1 分钟窗口、7 个 2 分钟窗口和 1 个 3 分钟窗口，≥5 分钟的一个都没有**。账面上覆盖了 63% 的空闲时间，实际上几乎什么都没解放。

### 4.4 学习有什么用

`eta.py eval`，学习后的估计器 vs 内置先验（完全不学习）：

| 历史 | 提升 | 原因 |
|---|---|---|
| 自动化的几秒钟小任务（MiMo） | +82.8% [+80.8, +84.5] | 默认节奏差 ×36 |
| 真人 + 自动化（wisp） | +38.2% [+29.6, +46.1] | 快问快答很多 |
| 贡献者 A（267 轮，中位 52 秒） | +27.7% [+19.2, +35.6] | 比默认快一倍多 |
| Fable 5 汇集 | +7.0% [+1.4, +12.0] | |
| 作者（68 轮） | +7.4% [−0.3, +13.7]；最近三分之一 +14.0% [+3.4, +22.0] | 近期权重 + 重校准 |
| 接近默认节奏的历史 | −3% 到 +5%，区间含 0 | 先验本来就合适 |

学习主要在“节奏离默认值很远”的人身上见效。除了校准，更长的记忆几乎没有用：对作者来说，更早历史的边际收益是 +1.0% [−2.4, +4.3]；有用的是加大近期运行的权重（两份历史选中 0.5 天半衰期，其余选 60 天——插件按人自动选）以及修正系统性偏长的 PIT 分位数重校准（P50 命中 67% → 54%）。“快问快答 + 工作”的双峰先验让新用户第一天的预测在 11 份历史上准了 **+8.1% [+6.9, +9.2]**，但没有改善可离开窗口（第 5 节），作为补丁放在 [research/](research/)。

### 4.5 模型之间有差异，但工作类型影响更大

| 模型 | 模型每步耗时（不含工具） | 停下来问你 | 内置先验 P50 命中 |
|---|---|---|---|
| Sonnet 4.6 | 7.2 秒 | 3% | – |
| Opus 5.5 / Opus 5 | 9.9 / 11.3 秒 | 6% / 3% | – |
| Fable 5 | 13.1 秒 | 1–4% | 55–57% |
| Opus 4.8 | 15.5 秒 | 10% | – |
| MiniMax M3 | 17.1 秒 | **33%** | 53% |
| Kimi K2.6 | 约 100 秒（该数据集缺工具时间） | 6% | 51% |

每步速度可以差一个数量级，有的模型问你的次数多得多；但对交互式编程，同一个内置先验对它们都合适（P50 命中 51–57%）。让先验失准的是工作类型。在按任务类型之外再按模型学节奏：Claude 系列内部反而略差（−1.5% [−2.4, −0.7]），只在混用多家模型的历史上有帮助（+1.4% [+0.6, +2.3]）。

## 5. 没有成功的尝试

保留在这里，因为对想做同样事情的人来说，这是最有用的部分。

| 想法 | 结果 |
|---|---|
| **自适应共形推断（ACI）** 调“可离开”的分位 | 如承诺的那样把*逐时刻*误差压到 20%，但大部分时刻的窗口不到 1 分钟、根本不显示；显示出来的长窗口在一位用户身上违约 34–51%。只用显示出的承诺来更新的变体，也不比插件调好的收缩强度好。 |
| 门槛：回放可信地证明能守住才显示 | 承诺更少，可靠性没提高（如 17% → 18%），对最需要它的用户（33%）也没用。 |
| 可离开窗口总是经过重校准 | 违约 17.4% → 21.4%。 |
| 双峰（快问快答 + 工作）先验 | 第一天准确度 +8%，可离开合计不变（24.5% → 24.7%）：有人变好（45% → 15%），有人变差（17% → 28%）。 |
| 相似的历史 prompt | ×2.60 → ×2.51。 |
| 等 15–60 秒看最初的动作 | 没有改善。 |
| 让大模型读任务 | 分辨力提高（相关 0.1–0.4 → 0.3–0.5），能认出的可离开任务 4% → 17%，但违约升到 28%。 |
| 让 agent 开局声明规模（注入“先列计划”） | 没有实测：信号会依赖模型，而且模型自己常常也不知道要多久。 |
| 完成时推送通知 | 不是我们要的（在开局就知道），而且各大 agent 都已经有了。 |

还有一个值得一提的 bug：账本反馈会在真实违约率的*上*界超过目标时让窗口更保守。几十个窗口的时候，上界几乎总会超过目标，于是在一份真实违约 15% 的记录上一路收紧到最保守——剩下的恰恰是过度自信的承诺（101 次 15% → 27 次 26%）。改成*下*界超过目标才收紧就好了。

## 6. 空闲时间到底在哪里

空闲时间是存在的——作者 78% 的 agent 工作时间都在 3 分钟以上的空当里——只是没法逐个任务*预测*出来。它可以被*聚合*出来：连续执行几个任务，总时长比单个任务可预测得多（按作者的历史重抽样）：

| 排队的任务数 | 总时长中位 | 80% 能保证至少 |
|---|---|---|
| 1 | 3.5 分钟 | 0.6 分钟 |
| 2 | 7.7 分钟 | 3.7 分钟 |
| 3 | 12.5 分钟 | 7.0 分钟 |
| 5 | 22.6 分钟 | 14.1 分钟 |
| 8 | 39.8 分钟 | 25.7 分钟 |

但不让 agent 交还控制权，正是 Codex `/goal`、“Ralph loop” 这类自主模式在做的事，它们的代价已经有大量记录：额度失控（一个 12 小时的 goal 用掉周额度的七成）、跑偏和范围蔓延、永远不宣布完成（跑了 65 小时，36% 的计划推倒重来）、为了继续运行而敷衍问题。而那些频繁的交还，恰恰是人在掌舵的地方。我们的结论是：这是换了个名字的同一种取舍，所以没有做。

## 7. 插件现状的利弊

**擅长的**

- 从 hooks 准确地切分轮次（见第 8 节），包括授权等待和后台 agent。
- 看清 agent 的时间花在哪里：按任务类型和仓库的轮次时长、最慢的命令。
- 诚实的时长区间，按你校准；如果你的节奏特殊，提升很大。
- **已知的慢操作正在执行时**（测试套件、构建）给出的可离开窗口是真可靠的——这时 agent 确实不可能需要你。
- 能自证：`eta.py eval` 和窗口账本。
- 隐私：本地 SQLite，不存 prompt 文字，不联网，不调用模型。

**不擅长的**

- 解放大块时间：可离开窗口本质上只有 1–2 分钟（4.2）。
- 这些窗口的可靠性因人而异（回放中违约 8–45%）。
- 开局的时长估计始终粗糙（×2.3–2.6）。

## 8. 在 Claude Code hooks 上踩过的坑

对任何基于 Claude Code hooks 做统计、成本追踪、通知的人都有用：

- **轮后辅助 agent 会重开已结束的一轮**。Stop 之后，Claude Code 自己的辅助 agent（比如“离开期间摘要”）会发出带着刚结束那一轮 `prompt_id` 的 `SubagentStop` / 任务事件。如果把“Stop 后同一个 prompt_id”当成续跑，27 轮里有 15 轮会一直挂到会话结束；186 个可离开窗口里有 119 个是给已经结束的轮次发的。只有主线程的工具事件（没有 `agent_id`）才代表真正的续跑。
- **`!` shell 命令不触发 `UserPromptSubmit`**。命令和输出在命令结束后才写进 transcript，用一个新的 `prompt_id`，然后模型接着回应。命令执行期间什么都观察不到。
- **按 Esc 不触发 `Stop`**，这一轮要等到下一条消息或会话结束才关闭。
- **后台任务用 `<task-notification>` prompt 唤醒 agent**：同一件事，新的 prompt_id。
- **子 agent 的工具调用带 `agent_id`**；transcript 把它们放在单独的文件里。
- **transcript 里没有授权弹窗**，导入的历史会少算“需要你”。

## 9. 方法上的教训

- 相信一个可靠性数字之前，把*整个*系统按时间重演一遍。事后调参给出 17%，按时间重演是 24.5%。
- 写下结论之前，先在更多人身上检验。我们曾经根据 6 份历史写下“16%”，又加了 5 份（29%）之后不得不收回。
- 算用户看得到的，而不是数学保证的（ACI 的逐时刻覆盖 vs 显示出的承诺）。
- 当心建立在不确定边界上的反馈回路（第 5 节的“棘轮”）。
- 最先该测的是风险曲线是不是平的：它直接告诉你，不依赖模型的承诺最多能有多长。
- 负面结果也是结果。这个项目的大部分价值在第 5 节。
- 一个工具上的坑：当匹配串就在同一条命令行里时，`pgrep -f` / `pkill -f` 会匹配到执行它的 shell 自己；我们有一个“还在跑”的实验，其实三个小时前就结束了。

## 10. 留给后来者的问题

- agent 能不能在早期给出一个*稳健*的规模信号（计划、步数），而不改变它的工作方式？能不能跨模型迁移？唯一一位 agent 会列计划的用户，相关性是 0.77。
- “离开的代价”会不会是比“承诺”更好的交互？比如对作者：离开 5 分钟，回来时 67% 的情况 agent 已经在等你（平均等了 3 分钟），33% 还在跑。这些概率可以用你自己的历史校准。
- 多会话并行：同时跑几个 agent 时，问题变成“下一个需要我的是哪个”——这是排序问题，比“保证”宽容得多。
- 带时间*和*注意力事件（授权弹窗、提问）的更大规模、经过同意的数据集，跨 agent（Codex、Cursor……），才能确定“风险曲线是平的”有多普遍。
